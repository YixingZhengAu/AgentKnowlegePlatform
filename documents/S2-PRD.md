## 1. 一句话定位

让用户把"答案埋在长文档里"的问题直接问出来,并拿到**有出处**的回答 —— 出处不是"大概在第三章",而是**点得开、看得见原文、含页码与截图**的引用。

**S2 是三条知识链路的最后一棒兜底**:只有精准问答(S1)与智能问数(S3)都没能给出答案时,才轮到文档 RAG 去文档里找。这一条决定了它的成败标准与别人不同:

```
① retrieve_exact_qa    高分命中 ─▶ 原样返回人工采纳的答案(零改写)
② retrieve_text2sql    命中模板 ─▶ 确定性数值结论
③ retrieve_doc_rag ◀── ★ S2 在这里(最后一棒)
      ├─ 有召回 ─▶ 概括作答,每个结论挂 [n] 引用
      └─ 无召回 ─▶ 兜底话术,不调生成模型
```

**核心主张(面试讲解的一句话)**:S1 靠"零改写"保准确、S3 靠"模板受约束改写"保准确,而 S2 是唯一真让模型概括的一环 —— 所以它的准确性不来自限制模型,而来自**三道可验证的工程动作**:切分质量(不腰斩语义)、图表看截图不信 OCR、以及**强制引用回显**(答案里每个结论都能点回原文,幻觉无处藏)。

## 2. 用户旅程(四步治理 + 第五步使用)

Step 1–4 发生在 `/ingest/document` 摄取台与审核台;Step 5 发生在 `/chat` 对话页。

### Step 1:上传 PDF

- 用户拖入或选择 PDF,填展示名(默认取文件名),提交即建 `documents` 行并启动加工任务。
- **只接受 `.pdf`**:选中其它格式时前端明确提示、后端入口校验并返回英文报错(D1)。
- 文档列表实时显示 `parse_status`(pending / parsing / parsed / failed),失败行直接显示失败原因 —— 文档列表是用户排查问题的唯一入口。

### Step 2:自动加工(一个 Job,五步,进度可见)

```
parse ──▶ clean ──▶ chunk ──▶ describe ──▶ stage
```

- **parse**:调常驻 MinerU 服务,拿到块序列(每块带类型、标题层级、页码、bbox)与图片。产物是**结构化中间表示**,不是裸 markdown。
- **clean**:用 MinerU 自带的噪声块标注去页眉页脚页码水印,**不用 LLM**。
- **chunk**:按标题层级递归切分,叶子超长按 token 上限二次切;**图表块整块不切**,并与前后各一段正文合成一个切片(孤立的描述块语义太薄)。
- **describe**:摄取阶段**唯一**的 LLM 调用,只处理含图表的切片 —— 把截图发给多模态模型写一段详细描述,写进切片正文(详见 §5-②)。
- **stage**:产物落 `staging_items`(`item_type='chunk'`)等待审核。
- 五步各自有日志与耗时;失败可从失败那一步重跑,不用从头再来;丢弃的块必须留痕(日志 + `documents.meta` 按类型计数)。

### Step 3:切片审核(唯一的人工关)

左右对照布局(沿用 S1 校对页的形状):

- **左**:原 PDF 预览;**右**:切好的切片列表,带标题层级、切片边界可见;图表切片旁并排显示截图与生成的描述。
- 三个动作,只有三个:
  - **编辑正文** —— 含直接改图表描述(模型写歪了人工顺手救);
  - **不采纳** —— 这条切片不进正式库(用现成的 `review_status`,与发布后的"禁用"是两件事);
  - **合并相邻切片** —— 修"一句话被切两半"这类切分事故;合并后 `seq` 不重排,留空洞(D6)。
- 不做"假设问题"面板、不做"校对解析文本"关(D2、D3)。

### Step 4:批量发布

审核完点发布,后端在**一个事务**里完成:approved 的切片写入 `chunks` → 批量算 embedding(64 条一批)→ `tsv` 由数据库生成列自动填充 → 写一条 `publish_records` 审计。

### Step 5:对话中兜底问答(运行时)

用户在 `/chat` 提问 → 精准问答未命中 → 智能问数判为非数据问题 → **进入文档 RAG**:

```
查询改写 ─▶ 双路召回(向量 Top-30 ∥ 全文 Top-30)─▶ RRF 融合
        ─▶ 重排取 Top-5 + 低分丢弃 ─▶ 上下文扩展(命中块前后各一块)
        ─▶ 生成:概括作答,每个结论挂 [n]
```

答案里的每个 `[n]` 都可点开,看到**该切片全文(文字 + 渲染出的截图)+ 文档名、页码、标题层级、检索分数**。检索全空或全部低分时,返回兜底话术,**不调生成模型**。

## 4. 功能需求分解

### F1 文档上传与解析
只收 PDF;调 MinerU;图片按内容哈希落盘;陌生块类型按噪声丢弃并留痕,**不因一个未知类型让整篇失败**(S1 踩过的坑);失败同时写 `parse_status='failed'` 与 `parse_error`。

### F2 切片审核
左右对照;编辑 / 不采纳 / 合并相邻;图表切片显示截图与描述并可编辑描述;审核动作沿用 S0 骨架的默认组件,只覆盖按钮文案。

### F3 发布与索引
批量发布;写 `chunks` 与算 embedding 同一事务;`tsv` 由生成列自动产生;一次发布一条 `publish_records`。

### F4 混合检索
查询改写(可开关)→ 向量 + 全文双路召回 → RRF 融合 → 重排 + 低分丢弃 → 上下文扩展。两条召回 SQL **都要过滤 `status='active'`**。命中结果必须随身带齐元数据(文档名、页码、标题层级、seq、分数、图表信息),否则引用回显无从生成。

### F5 生成与引用回显
prompt 里每个切片一个块、块头带 `[n]` 与标题层级;引用编号在后端生成 prompt 时就定死并同时写入 `message_citations.seq`,**不让模型自己编号**;点开 `[n]` 实时读库取全文与截图;无召回时用兜底话术且不调模型。

### F6 发布后运营
切片启用/禁用(禁用是软标志,被引用过的行不物理删,禁用同时清空向量);单文档重新摄取;这一块在主链路跑通后做。

## 5. 质量设计(本模块的技术灵魂,开发最先做)

| # | 机制 | 挡住什么错 |
| --- | --- | --- |
| ① | **切分质量是地基**:按标题层级切、图表整块不切、机器断言(不以半句结尾 / seq 连续 / token 在区间)+ 人眼过可视化 dump + golden 快照 | 语义被腰斩导致"召回了但答不出"—— RAG 最常见的失败,且发生在检索之前,调阈值救不回来 |
| ② | **图表看截图,不信 OCR**:表格既有 HTML 也有截图,**以截图为真相**,prompt 明确告知"OCR 可能错行漏行";描述必须先说行列维度再给关键行数值,小表逐行、大表自报截断 | OCR 静默错行。实测证据:某论文 Table 1 截图 22 行,而 HTML 只有 19 行且整行丢失 `Connected 1000` 与 `Softmax` —— 不看图就会把错数据当事实入库 |
| ③ | **描述进正文 = 图表进双索引**:描述作为纯文本写进 `content`,因而同时进 embedding 与全文索引 | 图片和表格"检索不到"(它们本身不参与任何索引) |
| ④ | **混合检索 + RRF + 真重排**:向量管语义、全文管关键词(型号、编号这类精确串),融合出 Top-30 后用 **cross-encoder** 精排到 Top-5 | 单靠向量搜不到型号串;单靠关键词答不了开放式问题;而向量把整段压成一个向量时,`DC` 与 `AC` 这种"一字之差"的信号会被淹没 —— cross-encoder 让问题与文档逐词交叉比对,把它捞回来 |
| ⑤ | **强制引用回显**:每个结论挂 `[n]`,点开看到全文 + 页码 + 截图;编号后端定死 | 幻觉与"看起来有据实际没有"。可点开的引用是最便宜、最有效的幻觉检测器 |
| ⑥ | **无召回不调模型**:整条链路"我找不到依据"这句话由 S2 说出口,直接返回配置话术 | 最后一道防线变成幻觉入口 |

配套一份**检索评测集**(照 S1 的人写题规格):四类题 —— 单切片可答 / 跨切片才可答 / 同领域但文档里没有(困难负例)/ 完全越界。**开放式与跨切片题占大头**,因为进到 S2 的问题天然是前两条链路答不了的难题。所有阈值(尤其低分丢弃线)由这份评测集实测定稿,**不凭感觉填**(S1 血泪:0.90 这类"看起来很稳"的阈值会把正例全挡在门外)。

## 6. 边界与依赖

- **与 S1 / S3 的边界**:S2 是串行链路的最后一棒,不与它们竞争位置。**精确的表内数值匹配归 S3**(D5)—— 本域负责"用自然语言问到这张表",不负责"精确查表里第 37 行"。
- **与 S4 的边界**:总 PRD 设想的"多链路并行执行再融合"属于 S4;S2 只做串行兜底(§8 冲突 1)。S2 交付的检索 stage 输出候选与分数,S4 接手后可替换裁决逻辑。
- **与 S3 的交界(已定)**:`refused_non_data` 改为转 `retrieve_doc_rag`,由 S2 在 C1 那次改动里一并完成,PR 中重点说明(§9 Q4)。
- **并行开发纪律**:严格遵守 `DOMAIN-DEV-GUIDE.md` —— 代码只落 `server/app/services/document/` 与 `web/src/domains/document/`;共享文件只碰冲突地图允许的"加一行";`core/chat.py` 插 stage 与集成者协调。
- **公共契约变更**(编号见各分册;**C7 重排模型落地**为 2026-08-24 新增,待提)。其中**两项已授权由 S2 自改**(集成者同意,PR 中醒目说明):
  - **C3** MinerU HTTP 客户端从 S1 域内上提到 `providers/`(不 import 兄弟域是红线,否则本域无法调用);
  - **C6** Provider 层 `ChatMessage.content` 扩为 `str | list[TextPart | ImagePart]`(图表描述要发图片),纯文本调用零改动。
- **外部依赖**:MinerU 常驻容器(CPU pipeline 后端);OpenAI 多模态与 embedding;
  **本地重排模型** `cross-encoder/ms-marco-MiniLM-L-6-v2`(部署形态见契约项 C7,沙箱阶段进程内直调)。
- **非目标(本期不做)**:PDF 之外的格式、块摘要与假设问题富化、独立的假设问题向量表、表格精确数值检索、答案一致性后校验默认开启、跨文档知识图谱。

## 7. 验收标准(DoD)

从浏览器完整走通以下故事,全程英文界面:

1. 上传 `company-handbook.pdf`,五步进度依次点亮,状态收在 `parsed`;上传一个 `.docx` 被明确拒绝并给出英文提示;
2. 审核台左侧看到原 PDF、右侧切片边界清晰无腰斩句;含表格的切片旁能看到表格截图与描述;
3. 在审核台改一条图表描述、合并一对被切碎的切片、不采纳一条噪声切片,然后批量发布;库里 `chunks` 有行、`embedding` 非空、`tsv` 非空、`publish_records` 多一条;
4. **图表可检索**:问一个只有图/表里才有答案的问题,能召回到那张图表所在切片;
5. **概括但有据**:问一个答案散落在两三个切片的问题,拿到概括性回答,每个关键结论挂 `[n]`;
6. **引用回显**:点开任一 `[n]`,看到该切片全文(截图正常渲染)+ 文档名 + 页码 + 标题层级;
7. **三 stage 依次出现**:同一 Agent 绑三个库,trace 面板可见 `retrieve_exact_qa` 未命中 → `retrieve_text2sql` 判为非数据 → `retrieve_doc_rag` 命中;
8. **无据则认怂**:问一个文档里没有的问题,拿到兜底话术,**且引用面板一条都不挂**;

   > ✅ **2026-08-25 修订(需求方拍板)**:原文要求"trace 里**没有 generate 这一段**"——
   > 该要求**改为不适用**,理由是实测发现的一个更准的判据。
   >
   > 原意是"没证据就别调生成模型,省钱且防幻觉"。但"有没有证据"这件事,**检索层判不准**:
   > 分数下限(`DOC_RAG_MIN_SCORE`)在评测集上正负两堆重叠,划哪儿都误杀真命中,已定不实现
   > (分册 2 §8)。于是链路只要索引非空就总会召回几片,`generate` 一定会跑。
   >
   > 换来的判据是:**让生成模型自己认怂,后端据此不落引用**(分册 3 §3b「区分派」)。
   > 实测证据(语料只有一篇 YOLOv3 论文时问 HC-300 保修期):重排最高分 −11.35、
   > guard 触发、模型如实回答"I don't have that information in the provided excerpts"——
   > **模型并没有编造**。所以"防幻觉"这个原始目的已经达到了,代价只是多付一次生成调用。
   >
   > 验收因此改成看**引用面板是否为空**(那才是用户真会看到的东西),
   > 而不是看 trace 里有没有 generate。
9. 冒烟脚本 `make smoke-s2`(照 `make smoke-s1` 四件套)全绿。

## 9. 开放问题(**2026-08-24 五项全部拍板**,保留问题原文以备回查)

| # | 问题 | 结论 |
| --- | --- | --- |
| Q1 | `tsv` 分词用 `simple` 还是 `english`? | **✅ 定:用 `simple`,生成列一行不动。** 全文腿的职责是抓型号/编号等精确串,词干化无收益,且省一次 migration |
