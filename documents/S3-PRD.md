## 1. 一句话定位

让业务用户把"公司数据库里才有答案的问题"(订单、库存、销售额……)在对话里直接问出来,并拿到**数值可信**的答案 —— 可信的来源不是 prompt 技巧,而是一条"**先治理、再模板化、最后受约束改写**"的三级漏斗:

```
① 语义层治理      给每张表每个字段写 description(AI 预填 + 人工修订)
② 意图与模板治理   AI 枚举可能被问的问题 → 人工筛选 → 每个意图沉淀一条可运行、
                  带参数定义的 SQL 模板,保存即发布
③ 运行时受约束改写  用户真实提问 → 意图匹配(与精准 QA / RAG 联合判定)→ 命中模板
                  → 只在模板允许的范围内改写 SQL → 只读执行 → 回答
```

**核心主张(面试讲解的一句话)**:运行时 LLM 从不"自由写 SQL",它只在人工审定过的模板边界内做**收窄式改写**(where 可改、select 只减不增、group by 只减不增)。准确率问题被前移到治理时解决,运行时只剩受控填空。

## 2. 用户旅程(五步,前四步是治理,第五步是使用)

以下 Step 1–4 全部发生在 `/ingest/text2sql` 治理台;Step 5 发生在 `/chat` 对话页。

### Step 1:连接数据源

- 用户新建数据源:填名称、host、port、database、username、password,点 **Test connection** 验证连通,通过后保存。
- **本期只支持 MySQL**(界面上 db type 固定为 MySQL,后端留 type 字段便于扩展)。
- 密码入库前 Fernet 加密(沿用 DB-DESIGN 既有约定,密钥 = env `SECRET_KEY`)。
- 连接账号**必须只读**:保存时后端探测账号权限,发现有写权限则给出警告(演示环境警告即可,不硬阻断,但会记录在数据源状态上);运行时执行层再加第二道防线(见 §5.4)。
- 保存成功后自动做一次 **schema 同步**:拉取该库全部表、字段、类型、注释、行数估计、每列采样值,写入语义层元数据表。之后可手动点 **Re-sync** 增量刷新。

**配套演示数据**:项目自带一个 MySQL 演示业务库 `clenergy_biz`(docker-compose 起容器,bootstrap.sh 建库灌数),≥5 张表,围绕总 PRD §2.0 的 Clenergy 业务:

| 表 | 内容 | 量级 |
| --- | --- | --- |
| `products` | 产品目录(HC 储能柜 / INV 逆变器 / EMS),型号、系列、单价 | ~20 行 |
| `customers` | 客户(工厂/园区/商业综合体),所在州(NSW/VIC/QLD/SA/WA)、渠道类型 | ~80 行 |
| `sales_reps` | 销售代表,姓名、负责州、团队 | ~15 行 |
| `orders` | 订单头:订单号、客户、销售、下单日期、状态、总额 | ~1200 行(近 2 年) |
| `order_items` | 订单行:产品、数量、成交单价 | ~3000 行 |
| `inventory` | 库存快照:产品、仓库、在手量、更新时间 | ~60 行 |
| `stock_movements` | 库存流水:出入库/盘点调整、数量、**每笔流水后的结存量 balance_after**、日期、单据号;快照在手量严格等于流水净额 | ~1400 行(近 2 年) |

(7 张表,满足"≥5 张、有订单有库存";数据全英文、澳洲州维度,符合 D5。)

### Step 2:字段语义层治理(description 是灵魂)

同步完成后进入 **Schema 治理页**,这是 S3 里最需要精心设计的页面:

- 左侧表列表(带启用开关:不启用的表不进入后续任何环节);右侧为选中表的**字段表格**:每行 = 一个字段,列为 `column_name / data_type / sample values(只读)/ display_name / description(可编辑)`。
- 每个 description 输入框旁有 **AI generate** 快捷按钮;表级还有 **AI generate all** 一键为整表(或所有空缺字段)批量预填。AI 生成的依据:字段名、类型、列注释、采样值、低基数枚举值、同表其他字段。**用户的工作模式是"改而不是敲"**:AI 预填 → 人工快速扫一遍修订 → 保存。
- 表本身同样有 display_name + description(同样带 AI 预填)。
- 低基数列自动识别并展示枚举值字典(如 `status: pending/paid/shipped/cancelled`),用户可为枚举值补业务含义;枚举字典会进入后续所有 prompt。
- 字段可标记 `sensitive`(生成的 SQL 禁止 SELECT 此列)与 `enabled`。
- 保存粒度:按表保存,随改随存,无需整库一次性完成。

> 这一步产出的 description 就是 semantic layer,是后面 AI 生成意图、生成 SQL 模板、运行时改写三个环节共同的理解基础,质量直接决定准确率。

### Step 3:意图(intent)生成与筛选

治理完 description 后,进入**意图管理页**:

- 用户勾选范围:全部启用表,或任选几张表。
- 点 **AI generate intents**:后端把所选表的表/字段 description、枚举字典、表关系喂给 LLM,让它**站在业务用户角度枚举"这些表可能被问到的问题"**。
- 每条生成的意图包含三样:
  1. **one-liner(一句话)**:必须以类型关键字开头 —— `Query: ...` 或 `Stats: ...`(中文语境即"查询/统计"打头),让列表一眼可分;
  2. **简述**:两三句说明这个问题在问什么、涉及哪些表;
  3. **类型**:`query`(查询,不含 GROUP BY)或 `stats`(统计,含 GROUP BY)。二分的原因:两类 SQL 的模板形态和运行时改写规则不同,提前分类能显著提升后面写 SQL 的准确率。
- 生成结果以卡片/表格列表展示,用户逐条**勾选采纳**:平时真会被问的留下,不会被问的不选。支持对文案就地小改。可多次追加生成(换一批表再生成,结果追加进列表,已采纳的不受影响)。
- 采纳后的意图进入"已采纳"列表,状态为 **draft**(还没有模板,尚不可被运行时命中)。

> 注意:这一步只是"梳理用户有哪些意图",还没开始写 SQL。

### Step 4:逐个意图配置 SQL 模板(治理的核心产出)

从已采纳列表点进任一意图,进入**意图详情页**:

1. **看**:意图 one-liner、简述、关联的表与全部字段(带 description)一屏可见。
2. **改**:简述可编辑 —— 把"这个问题到底要什么"写得更清楚,这段文字会直接进入生成 SQL 的 prompt。
3. **生成**:点 **AI generate SQL template**,后端用当下较强的 text2sql 手法(最小 schema 子集 + description + 枚举字典 + 表关系 + 类型分流的 prompt 策略 + 生成后静态校验 + 试执行自修)产出一条**真正可运行**的 SQL 模板。
4. **模板的四个能力**:
   - **可编辑**:SQL 文本可直接改(AI 可能写错);
   - **可运行**:点 Run,只读执行(强制 LIMIT + 超时),下方直接展示结果表格,让用户眼见为实;
   - **可定义参数**:这是模板的精髓。系统解析 SQL,把它拆成三个参数区(交互形态参考 `tmp/sql definition.png` 的折叠卡片式逐参数定义):
     - **筛选参数(where)**:每个 where 约束条件一张卡片 —— 标识、业务名、值类型、可取值/格式说明、提示词(告诉运行时改写器"用户怎么表达时映射到这个条件、怎么取值");
     - **输出参数(select)**:每个 select 输出列一张卡片 —— 标识、业务名、值类型、提示词。**select 集合 = 运行时输出的最大范围**;
     - **分组参数(group by,仅 stats 型)**:每个可分组字段一张卡片。**group by 集合 = 运行时分组的最大范围**。
     参数区由系统从 SQL 自动解析预生成,用户补充业务名和提示词即可(同样支持 AI 预填);
   - **可保存**:点 Save 即**发布**——意图状态变为 **published**,模板全量信息(SQL、参数定义、意图文案、类型)入库并建向量索引,从此可被运行时检索命中。已发布的意图可再编辑,重新保存即覆盖发布。

### Step 5:对话中真正问数(运行时链路)

用户在 `/chat` 提问后:

1. **意图匹配**:问题与已发布意图做语义检索。此判定**不是 text2sql 单独做主**——同一问题同时在精准 QA、文档 RAG、问数意图三路做候选评分,由路由联合判定走哪条链路(S3 阶段先实现问数侧的"意图检索 + 置信度输出"这半边,并入 S4 路由时零改动;S3 联调期用一个最简三路裁决顶上,见 §6)。
2. **命中意图** → 取出其已发布模板(SQL + 参数定义)。
3. **受约束改写**:LLM 拿到「用户原话 + 模板 SQL + 三区参数定义」,产出的**不是 SQL,而是一份结构化改写计划**(选哪些输出列、每个筛选参数取什么值/是否启用、stats 型选哪些分组列);后端代码把计划**确定性地**应用到模板 SQL 的语法树上,生成最终 SQL。三条铁律由代码结构保证而非 prompt 恳求:
   - **where**:只允许改写模板中已有约束的取值/开关(参数化的条件可改值、可禁用),不得引入模板外的新条件列;
   - **select**:只能从模板 select 集合中做子集筛选,**只减不增**;
   - **group by**(stats 型):只能取模板 group by 集合的子集,**只减不增**。
4. **执行与回答**:改写后的 SQL 过静态校验(仅 SELECT、无 DDL/DML、列表名合法、不碰 sensitive 列)→ 只读账号执行(强制 LIMIT、超时、行数上限)→ 以「自然语言结论 + 数据表格 + 最终 SQL 可查看」的形式回答,SQL 透明可复制,便于业务方校验。
5. **未命中**:意图检索低于阈值 → 本链路不作答,交回路由走其他链路或兜底(不允许凭空编 SQL)。

## 4. 功能需求分解

### F1 数据源管理
- F1.1 新建/编辑/删除 MySQL 数据源(name/host/port/database/user/password)
- F1.2 Test connection(实连验证,返回明确错误)
- F1.3 保存时密码加密存储;探测只读性并记录
- F1.4 首次保存自动 schema 同步;手动 Re-sync(保留人工已填的治理内容,只更新物理事实:新表新列进来、删除的标记失效、类型/采样值刷新)

### F2 语义层治理
- F2.1 表列表 + 启用开关;表级 display_name/description 编辑
- F2.2 字段表格:display_name/description 编辑、sensitive/enabled 开关、采样值与枚举字典展示
- F2.3 **AI 生成 description**:单字段按钮 + 表级批量按钮(只填空缺或全量重写,用户可选);生成为异步且逐字段回填,不阻塞编辑
- F2.4 枚举值业务含义补注

### F3 意图生成与管理
- F3.1 选表(全部/多选)→ AI 批量生成候选意图(one-liner 关键字前缀 Query:/Stats:、简述、类型)
- F3.2 候选列表:勾选采纳 / 忽略 / 就地编辑;可追加生成、可手工新建意图
- F3.3 意图状态机:`candidate(候选)→ draft(已采纳未发布)→ published(已发布)`;可停用/删除

### F4 SQL 模板配置(意图详情)
- F4.1 展示意图 + 关联表字段全景;简述可编辑
- F4.2 AI 生成 SQL 模板(生成 → 静态校验 → 试执行 → 失败自修,最多重试 2 次)
- F4.3 SQL 编辑器(语法高亮);Run 按钮 + 结果表格
- F4.4 参数定义区:自动解析 SQL 预生成 where/select/group-by 三区参数卡片;逐参数编辑标识/业务名/值类型/提示词;AI 预填
- F4.5 Save = 发布:校验(SQL 可运行、参数区与 SQL 一致)→ 入库 + 意图向量索引

### F5 运行时问数
- F5.1 意图语义检索(向量,输出 top-k + 置信度)
- F5.2 受约束改写(LLM 出结构化计划,代码应用到 AST)
- F5.3 SQL 安全闸(仅 SELECT / 白名单表列 / 禁 sensitive / 强制 LIMIT / 超时)
- F5.4 只读执行 + 结果组装(结论 + 表格 + 可展开的最终 SQL)
- F5.5 全程 trace(意图检索分数、命中模板、改写计划、最终 SQL、行数、耗时)按 S0 框架埋点

## 5. 准确率设计(本模块的技术灵魂,开发最先做)

| 层 | 机制 | 挡住什么错 |
| --- | --- | --- |
| 语义层 | 人审过的 description + 枚举字典 + 采样值 | 模型对字段的误解(最大错误来源) |
| 意图分型 | query/stats 二分,模板与改写 prompt 分流 | GROUP BY 类 SQL 的结构性写错 |
| 模板治理 | SQL 真跑通过 + 人工确认 + 参数定义 | 运行时从零写 SQL 的全部风险 |
| 受约束改写 | LLM 只出计划,AST 层执行"where 改值 / select ⊆ / group by ⊆" | 越权列、编造条件、幻觉聚合 |
| 安全闸 | sqlglot 静态校验 + 只读账号 + LIMIT/超时 | 危险语句与全表扫拖库 |

配套一份**离线冒烟评测**(参照 S1 `make smoke-s1` 套路):固定 15–20 个问题(覆盖 query/stats、改值、减列、减分组、该拒答的模板外问题),脚本逐个跑运行时链路,断言最终 SQL 与预期一致/结果非空/越权问题被拒,回归零成本。

## 6. 边界与依赖

- **与 S4 的边界**:三路联合路由属于 S4。S3 交付"问数侧检索 stage(输出候选 + 置信度)+ 单链路可跑通的问数问答";S3 联调期在自己域内用一个最简裁决(意图分 ≥ 阈值即走问数)演示,S4 接手后替换为正式路由,接口形状按 S4 需要预留。
- **与 S2 并行**:严格遵守 `DOMAIN-DEV-GUIDE.md` —— 代码只落 `web/src/domains/text2sql/` 与 `server/app/services/text2sql/`,共享文件只碰冲突地图允许的"加一行";`core/chat.py` 插 stage 与集成者协调。
- **摄取骨架的使用方式**:S3 的治理是**交互式配置**而非"上传→审核→发布"流水线,故 staging 审核台不是 S3 主路径;AI 批量生成(description 批量预填、意图批量生成)走 Job 框架跑异步任务,但产物直接以 candidate/draft 状态落自己域的表、在自己域的页面里筛选 —— 域内页面就是审核台。`staging_items` 旧定义的 `table_meta/metric/term` payload 随 §8 冲突一并废弃。
- **非目标(本期不做)**:多数据源同时问数、跨库 join、自动画图表、意图自动从未命中问题沉淀、MySQL 之外的 db、写操作、权限体系。

## 7. 验收标准(DoD)

从浏览器完整走通以下故事,全程英文界面:

1. 新建 MySQL 数据源连上 `clenergy_biz`,同步出 7 张表;
2. Schema 治理页对 `orders` 点 AI generate all,秒级看到 description 逐个回填,人工改 2 处保存;
3. 选 `orders + order_items + products` 生成意图,拿到 ≥8 条候选(Query:/Stats: 前缀清晰),采纳 4 条;
4. 进入 "Stats: Monthly sales by state" 类意图,AI 生成 SQL 模板,Run 出真数据,微调 where 参数提示词,Save 发布;
5. `/chat` 问 "How much did we sell in NSW last month?" → trace 可见:意图命中分数 → 模板 → 改写计划(where 州=NSW、时间=上月;select 减列)→ 最终 SQL → 答案含数值与表格;
6. 问一个模板范围外的列("profit margin",模板 select 里没有)→ 不编造,正常拒答/回落;
7. 冒烟评测脚本全绿。
