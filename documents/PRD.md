## 1. 背景与目标

### 1.1 背景

企业内部落地 AI 问答类应用时,最核心的矛盾不是"模型不够强",而是:

1. **不同业务场景对"容错率"的要求完全不同**。合同条款、报价规则、合规口径这类问题答错一次就是事故;而"某个功能怎么用""流程大概是什么"这类问题,给个方向性答案就够用。
2. **知识形态不统一**。一部分是人工精修的标准问答,一部分是海量非结构化文档,还有一部分根本不是文档 —— 而是数据库里的指标和明细。
3. **纯 RAG 兜不住全部**。把标准答案和普通文档丢进同一个向量库,高价值的精准答案会被稀释;而数据类问题(“上个月华东区营收多少”)在文档里永远找不到答案。

因此本系统的核心设计主张是:**按容错率对知识分层治理,再由 Agent 在回答时做路由,不同层走不同的检索与生成策略。**

### 1.2 产品目标

| 目标 | 说明 | 衡量方式 |
| --- | --- | --- |
| G1 讲清架构 | 面试中能用系统本身作为讲解载体,展示知识分层、路由、检索、生成、引用的完整链路 | 能在 10 分钟内完成一次端到端演示 |
| G2 效果直观 | 用户提问后,不仅看到答案,还能看到"Agent 为什么这么答" | 每次回答都有可展开的执行轨迹 + 引用来源 |
| G3 覆盖三类知识 | 精准问答 / 文档 RAG / 智能问数,三条链路都真实可用 | 三类各准备 1 个可演示业务场景 |
| G4 可扩展 | 知识类型、检索策略、Agent 配置均可插拔 | 新增一种知识类型不需要改动 Agent 核心逻辑 |

### 1.3 非目标(本版本明确不做)

- 不做多租户、组织架构、复杂权限体系(仅保留最简单的用户隔离占位)。
- 不做模型微调、不自建向量数据库、不做私有化部署方案。
- 不做多轮复杂任务规划(如"帮我把这份报表发给张总"这类带副作用的 Action)。
- 不追求高并发与高可用,单机可跑即可。

### 1.4 目标用户与使用者角色

| 角色 | 关注点 | 在系统中的动作 |
| --- | --- | --- |
| 知识运营(Knowledge Ops) | 知识质量、覆盖率 | 上传/编辑/审核三类知识 |
| Agent 配置者 | 场景效果 | 创建 Agent、绑定知识、调参、跑评测 |
| 终端用户 | 答得对不对 | 提问、看答案与引用、反馈点赞点踩 |
| 面试官(演示观众) | 设计能力 | 观看执行轨迹、看指标看板 |

## 2. 系统总览

### 2.0 演示业务背景(虚构公司,不具名)

为了让三类知识不是各说各话,而是围绕同一业务互相呼应,设定一家虚构公司。**按 D5,以下示例问题在实际演示数据中均为英文**(本文档为便于阅读用中文描述),地域维度用澳洲各州(NSW/VIC/QLD/SA/WA):

> **演示公司(不具名)**,做工商业储能柜与光伏逆变器的研发、销售与运维。有直销团队和渠道经销商,客户是工厂、园区、商业综合体。产品线:储能柜 HC 系列、逆变器 INV 系列、能源管理系统 EMS。

演示中的 Agent 人设:**"公司销售与售后助手"**,服务对象是一线销售和售后工程师。这个设定的好处是三类问题天然都会出现:

| 知识类型 | 该业务下的典型问题 | 为什么必须用这一类 |
| --- | --- | --- |
| **精准 QA** | "HC-215 的质保期是几年?""渠道商折扣最低能给到几折?" | 答错就是对客户的错误承诺,直接引发商务纠纷 —— 零容错 |
| **文档 RAG** | "储能柜现场安装对场地有什么要求?""EMS 告警 E304 怎么排查?" | 答案散落在几十页安装手册和运维 SOP 里,允许概括,要有出处 |
| **智能问数** | 「上个月 NSW 卖了多少?」「HC 系列各仓库近半年的出库量趋势」 | 答案根本不在文档里,在业务库里 |

**演示的高光时刻**——一个混合问题:

> "Which battery cabinet sold best in NSW last quarter, and what's its warranty policy?"(NSW 上季度卖得最好的储能柜是哪款,质保政策是什么?)

Agent 路由出**两条链路**:前半句走智能问数(查出货量排名),后半句走精准 QA(取质保标准口径),融合成一个答案。执行轨迹面板上能清楚看到"为什么选了这两个库、各自召回了什么"。这一个 case 就把整套架构讲完了。

**配套的演示数据**(随系统一起交付,全部为生成的假数据):

- 精准 QA:约 60 条(质保、折扣、认证、交付周期、对外承诺话术)
- 文档:6–8 份 PDF/Word(产品手册、安装规范、运维 SOP、售后政策)
- 业务库:`customers / orders / order_items / products / sales_reps / inventory / stock_movements` 七张表,近 2 年的模拟数据
  (S3 落地时定稿:**没有 `regions` 表** —— 州是 `customers.state` / `sales_reps.state` 上的字段,为一个五取值的维度单开一张维表只会让每条 SQL 多一次 join;`inventory` 与 `stock_movements` 是需求方要求补的库存快照与流水。建表与数据的唯一出处是 `docker/mysql/`,校验断言见 `server/scripts/verify_bizdb.py`)

### 2.2 一次问答的完整链路(核心流程)

```
用户提问
  ↓
[1] 查询预处理     指代消解 / 改写 / 语言识别 → 生成检索用 query
  ↓
[2] 路由决策       判断走哪几条知识链路(可并行、可多选)
  ↓
[3] 并行检索       ① 精准QA 命中?  ② 文档RAG 召回  ③ Text2SQL 生成SQL
  ↓
[4] 结果融合       按置信度与优先级排序、去重、裁剪到上下文预算
  ↓
[5] 答案生成       带引用生成 / 或直接返回标准答案(精准QA 高分命中时)
  ↓
[6] 后置校验       引用一致性检查 / 兜底话术 / 敏感词
  ↓
返回答案 + 引用 + 执行轨迹(Trace)
```

**关键设计点:精准 QA 具有"短路"能力**。当精准 QA 以高于阈值的相似度命中时,直接返回人工审定的标准答案,**不经过 LLM 改写**,从根本上消除幻觉风险。这是"不能出错的业务场景"的技术保障。

## 3. 模块一:知识整理模块

### 3.1 通用概念

- **知识库(Knowledge Base, KB)**:知识的组织单元。一个 KB 有且仅有一种类型(`exact_qa` / `doc_rag` / `text2sql`)。Agent 绑定的对象是 KB,不是单条知识。
- **知识条目(Knowledge Item)**:KB 内的最小单位,不同类型结构不同。
- **生命周期**:`草稿 → 待审核 → 已发布 → 已下线`。只有"已发布"的条目参与检索。
- **版本**:每次编辑生成新版本,保留历史与操作人,支持回滚。

### 3.1.1 通用摄取工作流(三类知识共用的骨架)

> **结构调整备注(2026-08,记录见 `documents/S0-PLAN.md` §5)**:本节的骨架
> (Source → Job → Staging → Publish 四张通用表 + 审核台)**继续有效**,S0 已交付;
> 但 §3.2–§3.4 三类知识各自的**具体 ingestion 流程(上传向导、加工步骤、审核表单)
> 与真实需求不符,待需求方确认后重写**,此前不作为开发依据。
> 前端导航现为 "Knowledge Ingestion" 二级菜单,三个域各一个空白壳页面
> (`/ingest/exact-qa` `/ingest/document` `/ingest/text2sql`),由各域开发者并行填充;
> Knowledge Bases 列表页已删除(`GET /api/kbs` 与 `knowledge_bases` 表保留)。

**重要架构决策**:三类知识的录入过程,形状是完全一样的 —— 用户上传一个"原料",系统异步加工出一批"候选",人工在审核台上确认,确认后才发布生效。把这个流程抽象成一套通用机制,三个模块只需要各自实现"加工逻辑"和"候选条目的编辑表单",其余(任务调度、进度反馈、审核台交互、发布与索引)全部复用。

```
①  上传原料          ②  异步加工(Job)         ③  人工审核(Staging)      ④  发布生效
  Source 入库    →   解析 + LLM 抽取/切分   →   逐条改 / 删 / 合并    →   写入正式表 + 建索引
  status=pending     进度可查、失败可重跑         批量通过、批量驳回          status=published
```

**统一的四张通用表**

| 表 | 作用 |
| --- | --- |
| `ingest_sources` | 用户上传的原料:文件或数据源连接。`kb_id / type / file_uri / status / meta` |
| `ingest_jobs` | 加工任务:`source_id / job_type / status(pending/running/succeeded/failed) / progress / step_logs / error` —— 前端轮询这张表画进度条 |
| `staging_items` | 加工产出的候选条目:`job_id / kb_id / item_type / payload(jsonb) / review_status(pending/approved/rejected) / confidence / origin_ref` |
| `publish_records` | 发布留痕:谁在什么时候把哪批候选发布成了正式知识 |

`payload` 用 jsonb 存,所以**三类知识的候选可以共用一张 staging 表**,差异只体现在 payload 结构和前端渲染的表单上。

**三类知识在这套骨架上的映射**

| 环节 | 精准 QA | 文档 RAG | 智能问数 |
| --- | --- | --- | --- |
| ① 原料 | 政策/规章文档、Excel QA 表 | PDF/Word/Markdown | 数据库连接串 |
| ② 加工 | 解析 → **LLM 抽取候选 QA 对** → 相似问扩写 → 冲突检测 | 解析 → 清洗 → 切分 → 富化 | 同步 schema → **LLM 预填业务名/描述/枚举字典** |
| ③ 审核 | 逐条改标准问与答案、勾选相似问、处理冲突 | 看切片是否被切坏、编辑/合并/禁用 | 勾选启用的表和字段、修正业务名、补口径 |
| ④ 发布 | 写 `exact_qa_items` + 一问一向量 | 写 `chunks` + 向量 + 全文索引 | 写 `table_meta / column_meta` + 术语向量 |

**这个抽象带来的三个好处**(也是面试时可讲的设计点):

1. **工作量大幅下降**:异步任务框架、进度条、审核工作台这三块最耗时的前后端工程,只做一遍。
2. **人在环路(Human-in-the-loop)是一等公民**,不是补丁。所有 AI 抽取的结果默认进 staging,**必须人工确认才生效** —— 这正好呼应本系统"按容错率治理知识"的主张。
3. **可扩展性落地**:新增第四类知识,只要实现一个加工器 + 一个审核表单,骨架不动。

### 3.2 类型一:精准问答库(`exact_qa`)

**定位**:零容错场景。合规口径、报价规则、产品硬参数、对外承诺话术。

**数据结构**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | uuid | ✓ | |
| `standard_question` | text | ✓ | 标准问法 |
| `similar_questions` | text[] | | 相似问,支持 LLM 自动扩写后人工确认 |
| `answer` | text | ✓ | 人工审定的标准答案,**原样返回** |
| `keywords` | text[] | | 用于关键词强匹配与消歧 |
| `effective_period` | daterange | | 有效期,过期自动失效(如报价单) |
| `tags` | text[] | | 业务域、产品线 |
| `status` | enum | ✓ | 生命周期状态 |
| `reviewer` / `reviewed_at` | | | 审核留痕 |

**检索策略(精确匹配检索器)**

1. 对 `standard_question` + 每条 `similar_questions` 分别做 embedding,建立"一问一向量"索引(而非把整条 QA 拼起来做一个向量 —— 这是提高命中精度的关键)。
2. 检索时:向量 Top-K 召回 → 关键词命中加权 → Cross-Encoder / LLM 重排,得到最终置信度 `score`。
3. 三档阈值(可配置):
   - `score ≥ 0.90`:**短路命中**,直接返回 `answer` 原文,标注"标准答案"。
   - `0.75 ≤ score < 0.90`:**待确认命中**,返回答案但附加"以下为标准口径,如与你的问题不完全一致请确认"提示,并把候选问题列出来让用户点选。
   - `score < 0.75`:不命中,交给其他链路。

**录入工作流(遵循 §3.1.1 骨架,前端 4 步向导)**

> ⚠️ 本小节流程**待需求方确认后重写**(精准 QA 真实 ingestion 流程与此不同,见 §3.1.1 备注)。

绝大多数精准 QA 不是手工一条条敲出来的,而是从既有的政策文件、产品规格书、售后条款里"提炼"出来的。所以主路径是**上传文档 → AI 抽取 → 人工审核 → 发布**:

| 步骤 | 前端界面 | 后端动作 | 用户操作 |
| --- | --- | --- | --- |
| **1 上传** | 拖拽上传区,选择本次抽取的业务标签 | 存文件 → 建 `ingest_source` → 派发 job | 上传《售后服务政策 v3.pdf》 |
| **2 抽取中** | 进度条 + 分步日志(解析中 / 抽取中 / 扩写中 / 查重中) | 解析 → LLM 分段抽取候选 QA → 相似问扩写 → 与已发布条目做冲突检测 | 等待(可离开页面,回来还能看到) |
| **3 审核** | **审核工作台**:左侧候选 QA 列表(带置信度、冲突标记),右侧编辑区,并排显示"原文出处"便于核对 | 提供逐条 patch、批量通过/驳回接口 | 改答案措辞、勾掉不靠谱的相似问、处理 3 条冲突、驳回 5 条无意义的 |
| **4 发布** | 发布确认弹窗(本次新增 X 条 / 更新 Y 条) | 写入 `exact_qa_items` → 逐个问法生成 embedding → 建"一问一向量"索引 | 点击发布,立刻可在对话中被检索到 |

**抽取环节的关键设计**

- **溯源必留**:每个候选 QA 记录它来自原文的哪一段(`origin_ref` 存文档 id + 页码 + 字符区间),审核时能一键对照原文。这是审核效率的决定因素 —— 让人凭空判断 AI 抽的对不对,几乎不可行。
- **置信度分档**:LLM 抽取时同时输出自评置信度,前端按"高/中/低"分组,低置信度的排在前面优先看。
- **冲突检测**:候选与已发布条目相似度 > 0.95 时标记冲突,审核台上并排展示新旧答案,让用户选择"替换 / 保留旧的 / 合并为相似问"。**避免同一个问题在库里有两个不同答案** —— 这是精准 QA 库最致命的质量问题。

**辅助入口(非主路径)**

- 单条手工新增 / 编辑 / 删除 / 下线。
- Excel 批量导入:走同一套 staging 流程,只是"加工"环节从 LLM 抽取换成表格解析。
- **未命中问题池转化**:用户提问没被满意回答时,问题进入待补录列表,运营一键"补答案 → 发布",形成从真实使用反哺知识库的闭环。这是整个系统最能体现"运营视角"的功能。

### 3.3 类型二:文档知识库(`doc_rag`)

**定位**:可容错场景。操作手册、内部 Wiki、会议纪要、行业资料。答案要求"有用、有据",允许概括与推理。

**数据结构**

- **文档(Document)**:`id / name / source_type(upload|url) / file_type(pdf|docx|md|txt|html|xlsx) / raw_uri / parse_status / meta`
- **切片(Chunk)**:`id / doc_id / seq / content / token_count / embedding / heading_path / page_no / summary`

**处理流水线(Ingestion Pipeline)**

> ⚠️ 本小节流程**待需求方确认后重写**(文档 RAG 真实 ingestion 流程与此不同,见 §3.1.1 备注)。

```
上传 → 解析(Parse) → 清洗(Clean) → 切分(Chunk) → 富化(Enrich) → 向量化(Embed) → 入库(Index)
```

1. **解析**:PDF 走版面解析(保留标题层级、表格转 Markdown);Office/Markdown/HTML 走结构化解析。扫描件走 OCR(可选,默认关闭)。
2. **清洗**:去页眉页脚、去重复空行、去水印文字。
3. **切分**:优先按标题层级递归切分,叶子节点超长时按语义 + token 上限(默认 512 token,overlap 80)二次切分。表格整块不切。
4. **富化**(提升召回质量的关键):
   - 为每个 chunk 拼接 `heading_path`(如「产品手册 > 安装 > 常见故障」)作为上下文前缀;
   - LLM 生成 chunk 级摘要与 3–5 个"该 chunk 能回答的假设问题"(HyDE 思路的离线版),这些假设问题也建向量索引;
   - 抽取实体/关键词供关键词检索使用。
5. **向量化**:文本嵌入模型(可配置),写入 pgvector。
6. **索引**:同时建立 BM25/全文索引,支撑混合检索。

**检索策略(混合检索器)**

1. **查询改写**:多路 query 生成(原句 + 2 条改写 + 关键词版),提升召回。
2. **双路召回**:向量检索 Top-30 + 全文检索 Top-30。
3. **融合**:RRF(Reciprocal Rank Fusion)合并。
4. **重排**:Rerank 模型取 Top-5,低于相关性阈值的丢弃。
5. **上下文扩展**:命中 chunk 自动带上相邻 chunk(前后各 1)与所属标题路径,避免答案被切断。
6. **生成**:带 `[1][2]` 编号引用的答案;检索为空或全部低分时,走"我在现有资料中没有找到依据"兜底,**不允许自由发挥**。

**运营功能**

- 文档上传(拖拽、批量)、解析进度与失败原因展示。
- **切片可视化**:能看到每份文档被切成了什么样、每个切片的向量化状态 —— 演示时这是最能体现"我懂 RAG 细节"的界面。
- 切片手动编辑/禁用/合并。
- 单文档重跑流水线。
- 检索调试台:输入一个 query,直接看两路召回、融合、重排前后的结果与分数。

### 3.4 类型三:智能问数库(`text2sql`)

**定位**:数据类问题。已经过治理的语义层,而不是「把库表直接丢给模型」。

**核心主张**:Text2SQL 的效果 90% 取决于语义层治理质量,而不是 prompt。因此本系统把「治理产物」作为一等公民的知识来管理。

> 本节按 S3 的实测结论重写(2026-08-23,原 v0.2 稿的一半被推翻)。**两条最重要的改动**:
> ① 运行时**不再自由生成 SQL**,改成命中一条人工验收过的模板再受约束改写;
> ② 语义层的一等公民从 `metric`/`term`/`rule`/`sql_example` 换成 **`sql_intent`(意图 = 模板 + 参数区)**,
> 那四张表随之废弃(理由见 `documents/DB-DESIGN.md` §4.9)。需求细节的唯一出处是
> `documents/S3-PRD.md`,表结构是 DB-DESIGN §4,逐段实测证据是 `documents/S3-PLAN.md`。

**数据结构**(表结构以 DB-DESIGN §4 为准)

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| **数据源** `datasource` | `db_type(mysql/postgres) / dsn_enc / readonly_confirmed` | 只允许只读账号;连接串 Fernet 加密落库,**明文永不出接口**;`readonly_confirmed=false` 时一切连库动作直接拒 |
| **表** `table_meta` | `table_name / display_name / description / row_estimate / enabled` | 业务命名与描述是模型能读懂的关键 |
| **字段** `column_meta` | `column_name / display_name / description / data_type / sample_values / enum_values / sensitive / enabled` | 枚举列要求逐值给业务含义;`enabled` 同时是执行闸白名单的来源 |
| **表关系** `relations` | `left / right / join_keys / source(fk\|heuristic)` | 演示库故意留了两条没建 FK 的逻辑关联,靠列名启发兜住 + 人工确认 |
| **意图** `sql_intents` ★ | `code / intent_type(query\|stats) / one_liner / brief / tables[] / sql / params / status(draft\|published\|disabled)` | **本域核心**:一条意图 = 一条人工验收过的 SQL 模板 + 它的参数区 |
| **相似问法** `intent_questions` | `intent_id / text` | 一条问法一个索引面 —— 这是意图被匹配上的主要途径 |
| **空路由负例面** `non_data_faces` | `text` | 「以上都不是」的示例(质保、安装等非问数问题),与意图进同一个向量空间 |
| **索引面** `intent_vectors` | `intent_id(可空) / face_type / text / embedding` | 一面一行;`intent_id IS NULL` 就是空路由伪意图 |

**治理链路(生成期,有人审)**

```
[1] 接库同步      只读账号 → information_schema + 采样/枚举识别 → 表/列/关系落库(默认全启用)
[2] 语义层治理    AI 批量/单点生成 display_name 与 description → 人工改 → 保存(停用不该进语义层的表列)
[3] 意图生成      选几张表 → AI 提 N 条候选(query/stats 分型 + 盲判复核)→ 审核台人工采纳成 draft
[4] 模板生成      AI 写 SQL → 9 条确定性静态校验 → 真库试执行 → 报错回灌自修 ≤2 轮
[5] 参数区拆解    AST 拆出三区(可改值的 filter / 可减的 output / 可减的 groupby)+ AI 预填提示词
[6] 验收发布      Run 出真数据 → 人工改 SQL/提示词/相似问法 → 发布(才建索引面)
```

**运行时链路(无人值守,不生成 SQL)**

```
[1] 语义路由      问题向量 vs 索引面(意图问法 + 空路由负例)→ 双门槛判定
                  命中负例面 → refused_non_data(**零 LLM**,这一步就结束)
[2] 改写计划      LLM 只输出结构化计划:filter 值 / 要减的列 / 要减的分组;越界就 feasible=false
[3] 确定性应用    代码校验计划 → sqlglot AST 重建 SQL(**模型的输出不直接进 SQL**)
[4] 执行闸        单条 SELECT + 表列白名单(= 启用的语义层)+ 强制 LIMIT + 读超时 + 只读账号
[5] 结果表达      代码从结果集算出结论句(不过生成模型,所以敢标 Verified)+ 数据表格 + 可展开可复制的最终 SQL
```

四个终态分开记账:`executed` / `refused_out_of_template`(模板管不到,给理由)/ `refused_non_data`(零 LLM)/ `execution_failed`(**永远算 bug**,不是业务边界)。

**三个刻意的设计决定**(实测逼出来的,展开见 `documents/S3-PLAN.md`)

1. **空路由是必需项**:非问数问题靠「索引里有更像的负例」拦下,靠调高分数阈值拦不住。
2. **采纳 ≠ 发布**:采纳(审核台)= 「这类问题值得做成模板」→ `draft`;发布(意图详情页)= 「这条模板我验收了」→ 才建索引面。
3. **口径焊死在模板里**:同一个指标不留第二份可漂移的定义,所以不要 `metric`/`term`/`rule` 表。

**运营功能**

- 连接数据源 → 一键同步库表结构 → 人工治理启用范围。**同步后表与列默认全启用**,治理动作是把不该进语义层的关掉(D2 页面上表清单与字段表格里的两列开关)。v0.2 写的「默认全不启用」在实测中被否:接一个新库之后什么都问不出来,且要先点几十下才能开始;真正的闸在别处 —— 语义层只收 enabled 的表列,而执行闸的白名单就是它。要改回默认全关是需求方一句话的事(`models/text2sql.py` 里 `enabled` 的 `server_default`)。
- 字段业务名/描述/枚举字典的批量填写:落成「单点建议 + 批量 Job」两个入口 × `fill`/`rewrite` 两个模式。★ `fill` 保住的是**库里的 DDL 注释**,不是人在治理页写的描述 —— 批量跑一次会把人写的描述换掉(D2 自测实测),页面提示按模式给了两句话。要不要给列级加 `human_edited` 保护是需求方的决定。
- **意图与模板的治理**(取代原稿的「指标与术语维护」与「示范 SQL 一键沉淀」):候选进审核台 → 采纳成 draft → 意图详情页生成模板、Run 出真数据、改 SQL 再 Run、编辑三区参数与相似问法 → 发布。「从历史成功问答一键沉淀」没做 —— 模板要人工验收,自动沉淀与这条路线的前提冲突。
- 问数的可见性落在两处:治理期是意图详情页的 Run 面板(走的就是运行时那道执行闸,所以 Run 过了就不会在运行时因闸失败),运行期是对话消息里可展开可复制的最终 SQL + trace 面板的五要素(意图分数 / 模板 id / 改写计划 / 最终 SQL / 行数+耗时)。

### 3.5 三类知识对比(演示时的核心一页)

| 维度 | 精准 QA | 文档 RAG | 智能问数 |
| --- | --- | --- | --- |
| 容错要求 | 零容错 | 可容错 | 数值必须准,表达可容错 |
| 知识来源 | 人工精修 | 已有文档 | 数据库 + 语义治理 |
| 是否经 LLM 改写答案 | **否**(高分短路) | 是 | 结论是,数值否 |
| 主要技术 | 一问一向量 + 重排 + 阈值 | 混合检索 + RRF + Rerank | 语义层 + Few-shot + SQL 校验沙箱 |
| 主要风险 | 覆盖率低 | 幻觉、召回不全 | SQL 错、口径错 |
| 对应缓解手段 | 未命中问题池 + 相似问扩写 | 引用强制 + 无依据兜底 | 白名单 schema + 静态校验 + SQL 透明 |

## 4. 模块二:Agent 与问答模块

### 4.1 Agent 定义

一个 Agent = 人设 + 绑定的知识 + 路由策略 + 生成策略 + 兜底策略。

**配置项**

| 分组 | 配置 | 说明 |
| --- | --- | --- |
| 基础 | 名称、头像、简介、欢迎语、推荐问题 | 演示体验 |
| 人设 | System Prompt、回答语气、语言、长度偏好 | |
| 知识绑定 | 可绑定 N 个 KB(任意类型混合);每个绑定项可设:优先级、启用开关、Top-K、相似度阈值、使用说明 | **使用说明**很重要:一句话告诉路由器"什么问题该用这个库" |
| 路由策略 | `auto`(LLM 路由) / `all`(全查再融合) / `rule_first`(规则优先) | 默认 `auto` |
| 生成 | 模型、temperature、最大 token、是否强制引用 | |
| 兜底 | 无召回话术、超时话术、是否允许通用知识回答(默认**否**) | |
| 安全 | 敏感词、是否允许输出 SQL、结果行数上限 | |

### 4.2 路由决策(Router)

这是整个 Agent 最能体现设计能力的部分,采用**规则前置 + LLM 判定 + 并行兜底**的三段式:

**第一段:规则前置(快、省、稳)**

- 精准 QA 库始终优先执行一次检索(成本低、收益高)。若高分短路命中 → 直接结束,不再调用其他链路。
- 命中显式规则(关键词、正则、意图标签)则直接指定链路。

**第二段:LLM 路由**

输入:用户问题(经改写)+ 各绑定 KB 的名称/类型/使用说明 + 最近若干轮对话。
输出:结构化决策
```json
{
  "targets": [
    {"kb_id": "kb_003", "reason": "问题涉及具体数值与时间范围,属于数据查询"},
    {"kb_id": "kb_002", "reason": "可能需要口径说明补充"}
  ],
  "need_clarification": false,
  "clarify_question": null
}
```
- 支持多选(一个问题可能既要查数,又要引用文档口径)。
- 支持"需要澄清":问题缺少必要条件(时间、范围、主体)时先反问。

**第三段:并行执行 + 兜底**

- 选中的链路并行执行,各自返回带 `score` 的候选。
- 若全部无有效召回 → 触发兜底策略(不允许模型凭空作答);同时把该问题写入"未命中问题池"。

### 4.3 结果融合与生成

- **优先级规则**:精准 QA(高分) > 智能问数(数值型问题) > 文档 RAG > 精准 QA(中分)。可配置。
- **上下文预算**:按优先级填充 context,超预算时截断低优先级内容,保证高价值证据不被挤掉。
- **引用规范**:每条证据带 `[编号]`,答案中的关键结论必须挂引用;前端点击引用可跳转到原文切片 / 原始 QA / SQL 与结果集。
- **一致性后校验**(可选开关):用一次轻量 LLM 调用检查"答案中的每个事实是否都能在给定证据中找到",发现不支持的句子则标红或重写。

### 4.4 对话工作台(前端体验)

三栏布局:

- **左栏**:Agent 列表 / 会话历史。
- **中栏**:对话流。流式输出;答案下方是引用卡片(可展开原文);数据类回答显示表格 + 图表 + 可折叠 SQL。
- **右栏(演示主角):执行轨迹面板**,时间线展示:
  1. 查询改写:原句 → 改写后
  2. 路由决策:选了哪些 KB、理由、耗时
  3. 各链路检索详情:召回条数、Top-N 及分数、被丢弃的原因
  4. Prompt 组装:最终喂给模型的 context(可展开查看,带 token 统计)
  5. 生成:模型、耗时、token 消耗、成本估算
  6. 后置校验结果
- 每条消息支持点赞/点踩 + 原因标签,反馈进入优化闭环。

### 4.5 会话与记忆

- 会话级多轮:保留最近 N 轮原文 + 更早轮次的滚动摘要。
- 指代消解:每轮提问前用轻量模型把"它/这个/上面说的"补全成完整问题,再进检索。
- 不做跨会话长期用户记忆(非目标)。

## 5. 模块三:观测与评测(支撑"效果可信")

面试展示中,"我怎么知道它变好了"是必问题,所以这个模块**在架构中全量保留**。

> **实施节奏(D4)**:本模块功能实现排在最后(S6),但它依赖的三样东西必须从 S0/S1 就位,否则后期要返工:
> 1. **Trace 全量落库**:每个 pipeline 阶段执行时同步写 `traces`,这是从 S0 就做的事(S1 起前端就要用它渲染执行轨迹面板)。评测跑分只是对 trace 做聚合统计,不需要新的采集逻辑。
> 2. **问答链路可被程序调用**:Agent 编排层的入口设计成 `run_chat(agent_id, question, *, stream=False) -> ChatResult`,HTTP/SSE 只是它的一层薄封装。评测执行器直接复用这个函数,零重复实现。
> 3. **数据表与接口口子先建好**:`eval_sets / eval_cases / eval_runs / eval_results` 四张表在初始 migration 里就建;`POST /api/evals/cases`(从某条消息一键存为用例)在 S1 就实现——因为这是评测集的唯一数据来源,越早开始攒,后期跑分才有真实用例。前端"加入评测集"按钮同期上线。
>
> 换句话说:**S0–S5 期间系统一直在为评测模块积累数据,S6 只做统计与对比界面。**

- **Trace**:每次问答落库完整轨迹(各阶段输入输出、耗时、token、成本),支持按会话/Agent/时间检索与回放。
- **评测集**:`question / expected_answer / expected_kb / expected_citation` 的用例集合,支持从真实会话一键加入。
- **批量跑分**:选定 Agent + 评测集 → 批量执行 → 指标:
  - 路由准确率(选对 KB 的比例)
  - 检索命中率(Recall@K / 引用命中率)
  - 答案质量(LLM-as-Judge 打分 + 人工复核)
  - 拒答率、平均耗时、平均成本
- **对比视图**:调整配置(如换阈值、开关 Rerank)后跑第二次,并排 diff 每条用例的变化 —— 这是最有说服力的演示素材。
- **未命中问题池**:低分/拒答/点踩的问题聚合,一键转为精准 QA 或标记为需补文档,形成闭环。

## 6. 技术方案

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite + Tailwind + shadcn/ui | 快速出好看的界面,演示观感重要 |
| 后端 | Python + FastAPI + Pydantic | 与 LLM 生态最贴合 |
| 编排 | 自研轻量编排(节点 + 有向执行 + Trace 埋点),不引入重框架 | **面试要讲"我自己怎么设计的"**,黑盒框架反而不利于讲解 |
| 存储 | PostgreSQL + pgvector | 一个库搞定关系数据 + 向量 + 全文,演示部署最简单 |
| 对象存储 | 本地磁盘(接口预留 S3/MinIO) | |
| 队列 | 起步用 FastAPI BackgroundTasks;文档量大时换 Celery/RQ + Redis | |
| LLM | 实际落地用 OpenAI:main = `gpt-5`(生成 / SQL 模板 / 受约束改写),light = `gpt-5-mini`(盲判 / 预填等轻量任务);Embedding 用 `text-embedding-3-small`(1536 维) | 分层用模型控成本,也是可讲的设计点。模型只从 `app/providers` 走,换供应商是改配置不是改链路 |
| Embedding / Rerank | 可配置的第三方 API 或本地 bge 系列 | 抽象成 Provider 接口 |
| SQL 安全 | sqlglot 解析 + 只读账号 + LIMIT/超时 | |
| 演示数据库 | **MySQL 8.4 独立容器**(端口 3307,只读账号 `biz_reader`) | S3 定稿:演示的是接入客户已有的库,而客户库以 MySQL 为多;独立容器也让业务库与系统自己的 PG 在演示里泾渭分明。假数据随系统交付(`docker/mysql/`) |

**核心抽象(保证可扩展)**

```python
class Retriever(Protocol):
    kb_type: str
    async def retrieve(self, query: Query, cfg: BindingConfig) -> list[Evidence]: ...

class Evidence:
    kb_id: str; kb_type: str
    content: str            # 喂给模型的文本
    score: float            # 归一化到 0-1
    citation: Citation      # 前端可跳转的溯源信息
    payload: dict | None    # 结构化载荷(如 SQL + 结果集)
```

新增一种知识类型 = 实现一个 `Retriever` + 一套管理 CRUD,Agent 编排层零改动。

## 9. 开发策略与顺序

> 这一章回答:系统不小,每个模块都横跨前端 / 后端 / 数据库,该按什么顺序开发。

### 9.1 两条核心原则

**原则一:垂直切片,不做水平分层。**

最容易犯的错是按技术层横向推进:先把三个模块的后端全写完 → 再统一写前端。这条路在这个项目上一定会翻车,因为:

- 后端"写完了"是没法验证的 —— 没有界面,你不知道审核工作台需要后端提供什么粒度的接口,写出来的 API 大概率要返工;
- 中间几周没有任何可演示的东西,而这个项目的**唯一目的就是可演示**;
- 一旦时间不够,你手上是三个半成品,而不是一个能跑的完整链路。

正确做法是一次只做一个模块,但**把它从数据库一直打通到前端能点**。做完精准 QA,系统就已经能演示"上传文档 → AI 抽取 → 审核 → 发布 → 提问命中标准答案"这个完整故事了 —— 哪怕文档 RAG 和问数一行都没写。

**原则二:公共骨架先抽干净,再做第一个模块。**

这跟原则一略有张力,但因为 §3.1.1 已经论证了三个模块的流程完全同构,骨架值得前置。**边界要卡死:只做已经确定三个模块都要用的东西,不做任何预测性抽象。** 判断标准是一句话——"这个东西第二个模块会不会原样再用一次?"答案不确定的,就等到第二个模块真的需要时再抽。

### 9.2 阶段划分

| 阶段 | 主题 | 产出 | 建议占比 |
| --- | --- | --- | --- |
| **S0** | 地基 | 见 §9.3,三模块共用的一切 | 15% |
| **S1** | 精准 QA 全链路 ✅ 已完成 | **样板工程**,后两个模块照它复制(见 `documents/S1-PLAN.md`) | 20% |
| **S2** | 文档 RAG | 摄取流水线 + 混合检索 + 切片可视化 | 20% |
| **S3** | 智能问数 | 语义层治理台 + Text2SQL 沙箱 | 20% |
| **S4** | Agent 编排与对话 | 绑定 + 三段式路由 + 融合 + 执行轨迹面板 | 15% |
| **S5** | 演示包装 | 示例数据、演示脚本、架构讲解页 | 10% |
| **S6** | 评测跑分 | 按 D4 决策,最后做;口子在 S0/S1 已留好 | 视时间 |

**为什么 S1 选精准 QA 当第一个模块**:它是三类知识里最简单的一个完整闭环 —— 摄取流程只有一步 LLM 抽取(没有切分、富化那么多环节),检索只有一路(没有混合检索、RRF、Rerank),生成甚至可以直接返回原文不调模型。用最短的路径把「上传 → Job → 审核台 → 发布 → 索引 → 检索 → 回答」这条主动脉打通,后面两个模块就是在成熟的模式上填内容,而不是边探索边写。

**S4 放在三个知识模块之后**的原因:路由器需要真实的多个 KB 才有意义。在只有一个 KB 时写路由,写出来的是假的。但要注意 —— S1 阶段就要有一个**最小可用的单 KB 问答链路**(`run_chat()`),否则没法验证检索效果;S4 只是把它从"直连一个 KB"升级成"路由到多个 KB"。

### 9.3 S0 地基阶段做什么(和不做什么)

**必须做**(这些是三个模块反复用的,晚做就要返工):

| 项 | 说明 |
| --- | --- |
| 全量 DB migration | 一次把所有表建好,**包括 eval 四张表和 §3.1.1 的四张通用表**。改表比建表贵得多 |
| Provider 抽象层 | `LLMProvider` / `EmbeddingProvider` / `RerankProvider` 三个接口 + 各一个实现。所有模块通过接口调用,不直接碰 SDK |
| **异步 Job 框架** | 三个模块的摄取都要用:提交任务、查进度、分步日志、失败重跑。起步用 FastAPI BackgroundTasks + `ingest_jobs` 表轮询即可,别上 Celery |
| **通用审核工作台组件** | 前端一个泛型组件:左列表 + 右编辑区 + 批量操作栏 + 原文对照面板。三个模块只传入不同的"条目渲染器" |
| Trace 埋点框架 | 一个 `@traced` 装饰器 / context manager,自动记录阶段名、输入输出、耗时、token。**S0 就做,否则后面补埋点是灾难** |
| `run_chat()` 统一入口 | 问答链路的唯一函数入口,HTTP/SSE 只是薄封装(见 §5 说明) |
| 前端壳 | 路由、三栏布局、API client、组件库、错误处理、Toast |
| 一键起环境 | `docker-compose up` 起 Postgres+pgvector;`make dev` 起前后端。**这个投入 1 小时,后面省几十次** |

**明确不做**:用户体系(先硬编码一个用户)、权限、KB 的复杂设置页、任何"以后可能会用到"的抽象。

### 9.4 每个模块内部的六步开发顺序 ★

这是最实用的部分。每个模块(S1/S2/S3)都严格按这六步走:

```
① 定契约   →  ② 后端核心逻辑(CLI 可跑)  →  ③ 包 API  →  ④ 前端界面  →  ⑤ 端到端  →  ⑥ 补边缘
```

**① 定契约(半天)**
先写 SQLAlchemy model 和 Pydantic schema,把这个模块的数据长什么样、API 收什么返什么定下来。此时不写任何逻辑。定完立刻生成前端 TS 类型(见 §9.5),前后端就有了共同语言。

**② 后端核心逻辑,先做成命令行能跑的(最重要的一步)**

不要一开始就写 HTTP 接口。把这个模块的"加工逻辑"写成纯函数 + 一个 CLI 脚本:

```bash
python -m scripts.extract_qa --file samples/售后服务政策.pdf --out out.json
python -m scripts.retrieve --kb kb_001 --q "HC-215 质保几年?" --verbose
```

这样做的好处极大:
- **调 prompt 不用点前端**。抽取质量的调优要跑几十次,每次都走一遍浏览器上传流程会把人耗死;
- 效果好不好当场就知道,不用等前端做完才发现抽出来的 QA 全是垃圾;
- 这些脚本后面直接变成 S5 灌示例数据的工具、S6 评测执行器的底层调用;
- 天然可写单测。

**这一步是整个方法论的核心:让"AI 效果"和"界面工程"两件事解耦,分别验证。** 因为它们的失败原因完全不同 —— 前者靠调 prompt 和参数,后者靠调交互,混在一起排查会成倍变慢。

**③ 包 API(半天)**
把已经验证过的函数包成 FastAPI 路由 + Job 派发。因为逻辑已经跑通,这一步纯机械劳动。

**④ 前端界面**
顺序也有讲究:**先做「审核台」,后做「上传页」**。审核台是这个模块的主战场、交互最复杂、也最能出演示效果;上传页只是个拖拽框,半小时的事。先做难的,免得时间被简单页面吃掉。做审核台期间,数据来源可以直接是第 ② 步 CLI 产出的 `out.json` 灌进 staging 表,不必等上传链路。

**⑤ 端到端跑真实数据**
用演示业务的示例文档,从浏览器上传开始完整走一遍,直到能在对话里问出来。这一步必然会暴露 3–5 个衔接问题,预留时间。

**⑥ 补边缘功能**
单条编辑、删除、下线、批量操作、导出、分页、搜索……这些**放到最后,并且是可砍的**。演示时用不到"删除一条 QA",但一定会用到"上传→抽取→审核→发布"。

### 9.5 契约先行:让前后端不打架

FastAPI 自带 OpenAPI,把它用起来:

```bash
# 后端改完 schema 后一条命令,前端类型自动更新
curl localhost:8000/openapi.json > openapi.json
npx openapi-typescript openapi.json -o web/src/api/types.gen.ts
```

前端所有请求都用生成的类型。后端改了字段名,前端立刻编译报错,而不是运行时才发现数据是 undefined。这在一个人同时写前后端时尤其省心 —— **让编译器帮你记住你两小时前在另一侧改了什么。**

### 9.6 每阶段的完成标准(DoD)

给每个阶段定一句硬标准,达不到就不进下一阶段。防止"看起来做完了"的假进度:

| 阶段 | 完成标准(必须能当场演示的一句话) |
| --- | --- |
| S0 | `docker-compose up` + `make dev` 后能打开页面,发一句话,DB 里能查到这次对话的完整 trace |
| S1 | ✅ 从浏览器上传一份业务手册 PDF,**校对解析文本**后触发抽取,在审核台采纳若干条,提问"HC 系列质保几年、末期容量保持多少"能原样返回标准答案并标注 Verified Answer(实测 0.780 命中、trace 只有 `retrieve_exact_qa` 没有 `generate` = 零改写)。**计划与实施记录:`documents/S1-PLAN.md`** |
| S2 | 上传产品手册,能在切片可视化页看到切片和向量状态;提问能返回带 `[1][2]` 引用、点击引用跳到原文切片 |
| S3 | ✅ 从浏览器接一条 MySQL 只读连接 → 同步 7 张表 → AI 生成表列描述并人工改 → 生成意图候选并采纳 → 一条意图从生成 SQL 模板到 Run 出真数据再发布 → 问「How much did we sell in NSW last month?」拿到结论 + 表格 + 可展开可复制的最终 SQL,trace 里看得到意图分数 / 改写计划 / 最终 SQL;问模板管不到的 profit margin 则给理由拒答、不编造。图表本期没做(结果表格 + 最终 SQL 已足够讲清口径)。**计划与逐段证据:`documents/S3-PLAN.md`** |
| S4 | 问 §2.0 那个混合问题,执行轨迹面板显示路由选中了两个 KB 及理由 |
| S5 | 断网状态下能完整跑一遍 10 分钟演示脚本 |
| S6 | 改一个配置,跑两次评测,并排看到哪几条变好、哪几条变差 |

### 9.7 常见陷阱

| 陷阱 | 后果 | 规避 |
| --- | --- | --- |
| 先写完三个模块的后端再写前端 | 三个半成品,API 大改 | 垂直切片(§9.1) |
| 一上来就上 Celery / Redis / 微服务 | 时间全花在基础设施上 | BackgroundTasks 够用,单进程单库 |
| 在浏览器里调 prompt | 迭代速度慢 10 倍 | CLI 先行(§9.4 第②步) |
| Trace 埋点留到最后 | 要改遍所有函数 | S0 就做装饰器 |
| S1 阶段就想把路由做好 | 只有一个 KB,做出来是假的 | S1 直连单 KB,S4 才做路由 |
| 边缘 CRUD 抢占主线时间 | 主流程不完整却在做删除按钮 | 六步法第⑥步,可砍 |
| 示例数据留到最后造 | 前面全程在用无意义的测试数据调效果 | S1 开始前先准备 2–3 份真实感文档 |

## 10. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 范围过大做不完 | 严格按 §9 的 S0–S4 优先级推进;每个阶段都保证独立可演示 |
| 演示数据不真实、说服力弱 | 用一个虚构但完整的业务背景(如"光伏储能设备公司"),三类知识围绕同一业务展开,互相呼应 |
| 涉及真实公司数据的合规问题 | 演示数据全部为生成的假数据,文档明示 |
| LLM API 成本/网络不稳定 | 关键演示路径支持"录制回放"模式:缓存过往 trace,断网也能演示 |
| 面试现场时间不够 | 准备 3 分钟版(只演示路由 + 三类各一问)与 10 分钟版两套脚本 |
